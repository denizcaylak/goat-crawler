# Recommendations for Production Deployment

If we want to take this project to production, the first thing we need to do is completely separate the crawler workers from the search API.  Right now, we're relying on SQLite in WAL mode and in-memory locks (`asyncio.Lock`) to handle concurrency on a single machine. That works great for a local prototype, but it will quickly bottleneck at scale. To fix this, we'd want to move the queue and the `Visited` URLs set into a fast, distributed NoSQL store like Redis or DynamoDB. This would allow us to spin up multiple crawler workers across different servers to scale horizontally. For the search backend, we should drop SQLite for something built specifically for heavy read loads and text search, like Elasticsearch. Also, real crawlers don't just visit a page once and forget it; we'd need to replace our strict "never crawl twice" rule with a polite recrawl scheduler that respects `robots.txt`, avoids hammering single domains, and keeps our index fresh.

As for the search experience itself, basic keyword counting (Term Frequency) is a good start, but it won't cut it for real users. We'd need to implement something closer to PageRank to measure actual link quality, plus add support for handling typos (fuzzy matching) and understanding semantic context. Finally, we can't run a production system blind. Both parts of the system need their own dedicated monitoring. On the crawler side, we need to watch out for queue backups and worker thread starvation. For the Search API, it's all about the user experience: tracking query latency, uptime, and click-through rates. Throw in some strict rate limiting to prevent DDoS attacks and manage costs, and we'd have a solid foundation for a real-world search engine.
